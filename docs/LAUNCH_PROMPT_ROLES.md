# Промпт запуска: анализ распределения ролей

Запускать облачную сессию на `rekc2004/combine`, ветка `main`. Основная сессия на **Opus (effort high)**: это аналитическая работа, где нужна сильная модель. В окружении нужен веб к документации Anthropic: `code.claude.com`, `platform.claude.com`, `www.anthropic.com` (плюс `docs.claude.com`, если приложение его принимает). Вставить блок целиком.

```
Ты работаешь в репозитории combine. Владельца нет на связи, переспросить нельзя. Твоя задача: анализ и рекомендация, не реализация. Существующие файлы не меняй, кроме создания новых.

Порядок, строго по шагам, результат каждого читай до следующего:
1. Прочитай целиком: README.md, core/CORE.md, core/pipeline.md, core/models.json, docs/MODELS.md, docs/EXPERIMENTS.md, docs/ROLES_INPUTS.md.
2. Проверь по актуальной официальной документации Claude Code и Anthropic (с версией и ссылкой), а не по памяти: (а) может ли субагент вызывать других субагентов, (б) какие есть способы оркестрации (субагенты, agent teams, workflows, скрипты) и их ограничения в облачных сессиях, (в) как задать модель и effort основной сессии и субагентам, (г) что известно о выборе модели для исполнителя и планировщика. Поиск и чтение отдавай combine-scout (Haiku), в задании явно перечисляй поля отчёта и метки [П]/[В]/[НП]. Недоступное помечай [НП], не выдумывай.
3. Определи роли и для каждой: модель, effort, набор инструментов, вход, выход, формат передачи задачи (шаблон спецификации и критериев приёмки), когда вызывать, чего не делать. Роли минимум: дирижёр, архитектор (спецификации и ревью), исполнитель-реализатор, разведчик, каркасщик, проверка безопасности, независимый проверяющий. Опирайся на принцип владельца из docs/ROLES_INPUTS.md раздел 4.
4. Посчитай стоимость альтернатив на типовом этапе (пример: этап «идентичность и токены» небольшого сетевого приложения), используя цены из docs/MODELS.md и данные первого прогона. Альтернативы: (A) всё делает архитектор Opus, как сейчас; (Б) дирижёр Opus, исполнитель Sonnet по спецификации, ревью Opus; (В) дирижёр Sonnet, архитектор Opus только спецификация и ревью, исполнитель Sonnet. Явно перечисли допущения (число токенов на шаг, число вызовов, кэш) и пометь все цифры как оценку. Не выдавай расчёт за измерение.
5. Опиши риски делегирования (потеря контекста, пропуск проверок дешёвой моделью, цена ревью, зацикливание) и способы их ограничить.
6. Предложи эксперименты для проверки рекомендации на реальном этапе проекта: что мерить, как сравнить A/Б/В, сколько повторов.
7. Результат: файл docs/ROLES_ANALYSIS.md. В начале краткое резюме для владельца на русском (до 20 строк): рекомендуемое распределение, чем оно лучше нынешнего, главные неопределённости. Дальше подробности. Отдельным разделом предложи правки core/pipeline.md и core/models.json в виде описания или патча, **не применяя их**.
8. Ветка exp/roles-analysis. В main не пушить, force-push не делать, pull request не открывать. Остановись после записи файла. В конце ответа итог до 12 строк.
```

Расход (для журнала): снять панель Usage до и после и записать в `docs/ROLES_ANALYSIS.md` не нужно: это делает владелец.
